# デシジョンテーブル (Decision Table Testing)

## いつ使うか (適用条件)

複数の条件の組合せによって挙動 (出力・アクション) が決まるとき (割引ルール・権限判定・バリデーションルールなど)。条件が2つ以上あり、「AかつBならX」のような複合ルールがある場合に使う。単一条件の範囲・閾値だけなら同値分割/境界値分析で足りる。

## 導出手順

1. 挙動を左右する**条件 (condition)** をすべて列挙する (例: 会員ランク、express指定、合計金額の閾値)
2. 条件の全組合せを機械的に作る (条件が n 個の二値条件なら 2^n 行)
3. 仕様上ありえない組合せ (不可能な組合せ) を消去する。消去した行は「なぜ不可能か」を記録する
4. 同一の出力・アクションになる行をまとめる (collapse)。ただし、まとめる際に条件の違いが結果に無関係であることを確認してからにする
5. 縮約後の表を最終成果物とする: `条件1 × 条件2 × ... × アクション`
6. **ルールが成立する行だけでなく、成立しない行 (否定側) も必ずテストケース化する**。「AかつBかつCならX」というルールに対し、Aのみ成立/Bのみ成立/どれも成立しない、といった否定側の行がXにならないことを検証しないと、ルールの境界が実装で正しく分離されているか (誤って広すぎる/狭すぎる条件で実装していないか) を検出できない

### デシジョンテーブルの書式例 (会員ランクがgoldかつ非expressかつ合計<=1000なら送料無料)

| # | rank=gold | express | 合計<=1000 | 期待結果 |
|---|---|---|---|---|
| 1 | Y | N | Y | 無料 |
| 2 | Y | N | N | 有料 |
| 3 | Y | Y | Y | 有料 (express は無料条件を満たさない) |
| 4 | N (silver/none) | N | Y | 有料 (rank条件を満たさない) |
| 5 | N (silver/none) | Y | Y | 有料 |
| 6 | Y | Y | N | 有料 |
| 7 | N (silver/none) | N | N | 有料 |
| 8 | N (silver/none) | Y | N | 有料 |

行4・5・7・8は「ルールが成立しない」否定側であり、無料にならないことの検証として必須 (成立側 #1 だけでは、rank/express/合計条件のどれが実装で正しく分離されているか判別できない)。

## 実装パターン

言語非依存の原則: デシジョンテーブルの各行を1テストケースに対応させ、表そのものをコメントとして残す。行の追加・削除はテストケースの追加・削除と1対1にする。

```python
# decision table: free shipping = gold AND NOT express AND total<=1000
@pytest.mark.parametrize("rank,express,total,expected", [
    ("gold", False, 1000, "free"),      # row 1
    ("gold", False, 1001, "charged"),   # row 2
    ("gold", True, 1000, "charged"),    # row 3 (negative: express)
    ("silver", False, 1000, "charged"), # row 4 (negative: rank)
])
def test_shipping_fee_rules(rank, express, total, expected):
    ...
```

## 限界と誤用

- 条件数が多いと 2^n で組合せが爆発する。関連しない条件は表を分ける、または独立パラメータが多い場合はペアワイズ (`pairwise.md`) を検討する
- 「同一の出力になる行をまとめる (collapse)」を早まって行うと、実際には結果に影響する条件を見落として縮約してしまう。まとめる前に、条件の違いが本当に結果と無関係かを確認する
- 条件同士に依存関係がある場合 (ある条件が別の条件の値によって無意味になる) は、そのまま 2^n 展開すると無意味な行が増える。手順3で機械的に除外する
