# ペアワイズテスト (Pairwise Testing)

## いつ使うか (適用条件)

独立に選べるパラメータが3つ以上あり、全組合せをテストすると爆発する (n 個のパラメータ、各パラメータが平均 m 個の値を持つ場合、全組合せは m^n まで増加)。設定フラグ、環境マトリクス (OS × ブラウザ × 解像度)、フォームの選択肢などがこれに該当する。

**判定基準: 条件間にビジネスルールがある場合はデシジョンテーブル (`decision-table.md`)。単に独立したパラメータの組合せが多いだけならペアワイズ。**

例: 割引ルール「金額かつ会員ランクかつ時期」→ ルール間に依存関係 → デシジョンテーブル。設定フラグ「言語 × テーマ × フォントサイズ × 通知設定」→ 独立、組合せが爆発 → ペアワイズ。

## 導出手順

1. テスト対象の**パラメータと各パラメータの取りうる値を列挙する**
   - 例: `OS: {Windows, macOS, Linux}, Browser: {Chrome, Firefox, Safari}, Arch: {x86, ARM}`

2. **制約 (あり得ない組合せ) を明示的に列挙する**
   - 例: Safari は Windows では動作しない、ARM は Windows では非対応

3. **2-way (ペア) 網羅**: 任意の2パラメータを選んだとき、その2パラメータの全組合せが少なくとも1テストケースに含まれるようにする
   - 手作業は困難 → ツールで生成

4. **組合せ生成方法を選ぶ**:
   - **PICT (Pairwise Independent Combinatorial Testing, Microsoft OSS)** — 主ツール。モデルファイル形式で制約を記述、結果は配列出力
   - **代替ツール**: AllPairs, ACTS (NIST) など
   - **手作業**: パラメータが少ない (2〜3個) 場合、または直交表 L4, L8, L9 を使う

5. 生成結果の各行が1テストケース。実装側で制約をフィルタして有効なテストケースのみを実行する

## 実装パターン

言語非依存の原則: PICT やツールで生成した組合せを、そのまま parametrize の配列に対応させ、生成に使ったモデルファイルをコメントとして残す。

PICT モデルファイル例 (3パラメータ × 制約):

```
OS: Windows, macOS, Linux
Browser: Chrome, Firefox, Safari
Resolution: 1080p, 2K, 4K

# Constraints: Safari only on macOS, 4K only on macOS/Linux
IF [OS] = "macOS" THEN [Browser] <> "Chrome";
IF [OS] = "Windows" THEN [Browser] <> "Safari";
IF [Resolution] = "4K" THEN [OS] <> "Windows";
```

PICT 実行結果 (2-way coverage):

```
Windows	Chrome	1080p
macOS	Safari	2K
Linux	Firefox	4K
...
```

テスト実装例:

```python
# pairwise model: see references/pairwise.md
# Generated by PICT with 2-way coverage and constraints
@pytest.mark.parametrize("os,browser,resolution", [
    ("Windows", "Chrome", "1080p"),
    ("macOS", "Safari", "2K"),
    ("Linux", "Firefox", "4K"),
    ...
])
def test_env_matrix(os, browser, resolution):
    ...
```

## 科学的根拠

- Kuhn, D.R., Wallace, D.R., Gallo, A.M. (2004) "Software Fault Interactions and Implications for Software Testing", IEEE Transactions on Software Engineering, vol. 30, no. 6, pp. 418-421 — 実証研究。NASA および NIST の複数のソフトウェアシステムを対象に、欠陥を引き起こす変数間相互作用の実例を分析。結果: **大多数の欠陥は2個以下のパラメータの相互作用で引き起こされる** (相互作用が3つ以上の変数に及ぶ欠陥は数%以下)。ペアワイズ (2-way) 網羅で体系的に多くの欠陥が検出できる理論的根拠を与える

- NIST Automated Combinatorial Testing for Software (ACTS) — NIST が公開している実装資料・ツール・論文。「ペアワイズ網羅で実運用ソフトウェアの約60〜95%の欠陥が検出可能」という実績ベースの知見を提供。t-way (t=3,4,...) テストへの拡張ガイドも含む

## 限界と誤用

- **3変数以上の相互作用が既知の場合**: ペアワイズは不十分。その場合は t-way テスト (t=3 or higher) を検討する。ツール (PICT, ACTS) で t-way に対応しているか確認する

- **デシジョンテーブルとの混同**: パラメータの組合せが多いという理由だけでペアワイズを選ぶと、ビジネスルール (割引・権限・バリデーション) を無視して薄いテストになる。条件間にルールがある場合は先にデシジョンテーブルを優先し、その後に独立パラメータの組合せをペアワイズで補足する

- **制約の見落とし**: あり得ない組合せを見落とすと、テスト実行時に大量の skip/fail が出る。あらかじめ仕様・実装双方から制約を洗い出し、ツールに入力してから生成を行う

- **2-way で足りない根拠の不足**: プロジェクトの品質要件によっては 2-way では不十分なこともある。高信頼性システム (医療・航空・金融) では、設計段階で t-way の方針を明記する
